## 上下文

当前仓库仍是 Electron + Vue 3 的初始模板，尚未建立用户态、业务 API 封装或账户模块。项目领域是音乐播放器，后续很可能同时存在桌面端和网页端访问场景。用户已明确要求本次扫码登录直接请求 `https://ncmapi.iamxyj.com/`，并沿用 `@neteasecloudmusicapienhanced/api` 的二维码登录接口语义，以便未来网页端继续复用同一套实现思路。

当前 Electron 预加载层只暴露空的 `api` 对象，主进程也没有任何业务代理逻辑。基于这一现状，本次设计需要在尽量少引入 Electron 专有耦合的前提下，完成二维码登录闭环、登录态持久化和会话恢复。

## 目标 / 非目标

**目标：**

- 在渲染层建立可复用的登录服务，直接请求远端 NCM API 完成二维码登录流程。
- 支持获取二维码、轮询扫码状态、处理待扫码/待确认/成功/过期四类核心状态。
- 在登录成功后持久化单账号登录态，并在应用启动时恢复当前会话。
- 恢复成功后请求当前用户基础信息，用于判断是否已登录和驱动界面展示。
- 提供退出登录能力，退出后清空本地会话并回到未登录状态。

**非目标：**

- 不在本次设计中引入主进程代理层、IPC 登录服务或服务端中转。
- 不实现多账号管理、账号切换、云同步、复杂刷新令牌机制或账户中心。
- 不把扫码登录与播放、歌单同步、个性化推荐等后续业务能力绑在同一次变更中。

## 决策

### 1. 在渲染层直接封装远端 API 调用

选择在 renderer 中实现 `qr-login` 服务模块，统一处理二维码 key 获取、二维码 URL 生成、扫码状态轮询、当前用户信息查询和退出登录。

原因：

- 用户已明确要求采用渲染层直连方案，方便未来网页端复用。
- 当前项目还没有业务 IPC 和主进程服务框架，直接在渲染层实现能减少前期样板代码。
- 二维码登录流程本身主要是 HTTP 请求与状态机，更适合抽象为跨端可复用的前端服务层。

备选方案：

- `main + preload + renderer` 分层：Electron 边界更清晰，但会引入桌面端专有接口，不利于网页端复用。
- 独立认证域服务并引入全局状态管理：长期更完整，但对于当前空白仓库来说建设成本偏高。

### 2. 将登录流程建模为显式状态机

登录状态统一收敛为 `idle`、`loadingQr`、`waitingScan`、`waitingConfirm`、`authenticated`、`expired`、`error`。

原因：

- 二维码登录天然是阶段型流程，显式状态比组件内散落的布尔值更容易维护。
- 后续网页端可以沿用同样的状态枚举和视图映射。
- 明确状态也便于限制轮询生命周期，避免重复轮询或过期后仍继续请求。

备选方案：

- 仅依赖接口码与局部变量驱动 UI：实现更快，但状态分散，错误处理与重试逻辑容易失控。

### 3. 使用本地持久化保存单账号会话

登录成功后将 cookie 或等效登录凭证保存在渲染层可访问的本地存储中，并在应用启动时读取；读取到会话后，以“获取当前账号信息是否成功”作为恢复是否有效的判据。

原因：

- 当前范围只要求单账号，本地持久化即可满足需求。
- 以用户信息查询作为恢复校验，能避免仅凭本地值判断导致的伪登录状态。
- 该策略跨 Electron 和网页端都容易复用。

备选方案：

- 仅保存在内存中：应用重启后丢失登录态，不满足需求。
- 引入更复杂的安全存储方案：长期可考虑，但不是本次最小闭环所必需。

### 4. 用轮询驱动扫码状态更新，并限定刷新与终止条件

二维码生成后启动定时轮询；当状态变为待确认、登录成功、二维码过期或发生不可恢复错误时，更新本地状态并停止当前轮询。二维码过期后只允许显式刷新创建新的 key 与轮询周期。

原因：

- 二维码登录接口本身是查询式模型，轮询是直接且稳定的实现方式。
- 显式终止条件能防止界面重复请求和资源浪费。
- 让“过期后重新生成二维码”成为明确操作，可以减少状态混乱。

备选方案：

- 页面层自由创建多个轮询任务：实现简单，但极易造成竞态和重复请求。

### 5. UI 先以单卡片闭环承载登录体验

初期在登录区域提供统一卡片，未登录时展示二维码和状态文案，登录后展示当前用户基础信息与退出按钮。

原因：

- 当前项目没有现成设计系统，单卡片方案更适合快速建立闭环。
- 登录视图聚焦状态切换，有利于后续替换为更完整的页面布局，而不影响底层服务。

备选方案：

- 先拆成多个页面或复杂账户区域：当前收益不高，会放大结构调整成本。

## 风险 / 权衡

- [远端接口跨域或可用性波动] → 在设计中要求统一网络错误态、超时提示和可重试入口，并将接口基地址集中配置。
- [渲染层持久化存在安全边界弱于主进程方案] → 本次仅保存单账号会话并明确这是为跨端复用做的阶段性选择，后续如果安全要求提升再迁移存储方案。
- [轮询造成重复请求或竞态] → 将轮询控制集中到登录服务，要求启动前先清理旧定时器，状态终结后立即停止轮询。
- [本地会话失效但界面误判为已登录] → 应用启动恢复时必须通过“获取当前用户信息成功”校验会话有效性，失败则清理存储。
- [当前仓库尚无统一状态管理] → 本次先把状态收敛在登录模块和登录视图附近，避免过早引入全局状态工具。

## Migration Plan

1. 新增渲染层登录服务、接口封装和本地存储读写逻辑。
2. 在现有首页接入登录卡片，替换模板示例内容。
3. 联调远端 NCM API，验证二维码生成、状态轮询、成功登录、恢复会话和退出登录。
4. 若上线后发现远端接口不稳定，可先保留 UI 与状态模型不变，再将底层请求基地址切换到其他兼容服务或后续主进程代理实现。

## Open Questions

- 暂无阻塞本次提案的开放问题。默认使用远端兼容接口返回的 cookie 作为会话载体，并以当前用户信息接口作为恢复校验依据。
