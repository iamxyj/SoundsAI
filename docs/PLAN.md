# 音乐 MVP 子任务拆分方案（基于现有 Electron + Vue 空壳）

## Summary
当前仓库还是模板状态，业务代码几乎为零，且尚未接入 `@neteasecloudmusicapienhanced/api`。基于你确认的方向，这次拆分按以下边界执行：

- 范围：前后端联调版，但不自建后端，直接消费现成 npm 接口能力
- 身份：首期必须登录
- 接入：渲染层直连接口，尽量保持未来迁移到网页端的复用性
- 里程碑优先级：先跑通“登录 -> 搜索 -> 播放”最短闭环，再补首页推荐和历史增强

## 实施策略
可选拆法有三种：

1. 纵向切片优先（推荐）
- 先做一条可演示、可验收、可持续扩展的用户闭环，再逐步补全推荐、历史、异常兜底。
- 适合当前仓库，因为基础设施少，先拿到真实播放结果最能降低不确定性。

2. 分层基础设施优先
- 先把 API SDK、状态管理、播放器内核、路由、持久化一次性铺好，再接页面。
- 结构更整齐，但前期产出慢，容易在“架子工程”上花太久。

3. 功能面并行铺开
- 登录、首页推荐、搜索、播放器一起推进。
- 视觉进展快，但当前仓库太空，容易出现状态模型反复返工。

本次建议采用 1：纵向切片优先。

## Key Changes
### Phase 0：项目基建落位
- 安装并验证 `@neteasecloudmusicapienhanced/api` 及其调用前置依赖。
- 为渲染层建立统一的数据访问层，禁止组件内直接散落请求。
- 补齐页面骨架与基础导航，只保留首期需要的 4 个区域：登录、搜索、首页、播放器。
- 引入统一状态管理方案，至少覆盖 `auth`、`search`、`player`、`history`、`recommendation` 五类状态。
- 定义错误提示和加载态规范，避免后续每个页面各写一套。

### Phase 1：登录 -> 搜索 -> 播放闭环
- 登录：
  - 实现登录表单、登录状态保存、启动时会话恢复、失效态回退。
  - 明确“未登录不可用”页面流转。
- 搜索：
  - 接入歌曲/歌手/专辑/歌单搜索。
  - 首期主结果以“歌曲可播放”为主，歌手/专辑/歌单先作为辅助结果或 tab。
  - 处理空结果、接口失败、频繁搜索防抖。
- 播放：
  - 支持点击搜索结果即播放。
  - 落地基础播放器状态：播放/暂停、上一首/下一首、进度、音量、当前歌曲信息。
  - 建立最小播放队列，保证“从搜索结果连续播放”成立。
  - 处理歌曲不可播、URL 失效、播放失败时的提示与自动跳过。

### Phase 2：首页推荐与内容发现
- 首页推荐流：
  - 接入推荐歌曲、推荐歌单、热门兜底内容。
  - 支持“换一批”刷新，且避免完全重复返回。
- 内容卡片：
  - 推荐歌曲卡片可直接播放或加入队列。
  - 推荐歌单卡片可进入详情页或展开歌曲列表。
- 基础分类：
  - 首期只保留 2 到 3 个入口，建议 `推荐 / 热门 / 新歌`。
- 兜底策略：
  - 推荐为空时回退热门内容。
  - 未取到个性化内容时给出平台默认流。

### Phase 3：播放队列与播放模式补全
- 完成完整队列视图：当前歌曲、待播列表、切歌顺序。
- 支持三种模式：单曲循环、列表循环、随机播放。
- 保证切模式后下一首逻辑一致，且刷新页面后关键状态可恢复。
- 明确队列来源优先级：
  - 从搜索结果播放时，默认以当前搜索结果集作为临时队列。
  - 从推荐流播放时，以当前推荐列表作为临时队列。
  - 手动追加的歌曲进入统一待播队列。

### Phase 4：历史记录与轻量个性化增强
- 持久化最近播放、搜索点击、播放完成摘要。
- 首页推荐在已有接口支持下，接入基于登录态的增强结果。
- 最近播放作为独立入口展示，并可快速续播。
- 明确本地与服务端状态边界：
  - 会话与推荐依赖服务端。
  - UI 恢复态、最近一次播放上下文可先本地持久化。

### Phase 5：异常与可发布质量收口
- 补齐无网、超时、接口报错、资源失效、空列表等状态页与提示。
- 做一次播放主链路验收，确保错误不会让播放器彻底失控。
- 整理桌面端壳层职责，只保留窗口和运行时能力，不把业务逻辑绑死在 Electron。

## Public APIs / Interfaces / Types
内部需要尽早定下这些前端模型，避免后续反复改状态结构：

- `AuthSession`
  - `userId`、`nickname`、`avatarUrl`、`token/cookie摘要`、`loginStatus`
- `Song`
  - `id`、`name`、`artistNames`、`albumName`、`coverUrl`、`durationMs`、`playable`
- `SearchState`
  - `keyword`、`activeTab`、`loading`、`results`、`error`
- `PlaybackQueue`
  - `currentSongId`、`sourceType`、`songIds`、`pendingSongIds`、`mode`、`volume`、`progressMs`
- `RecommendationFeed`
  - `sections`、`refreshToken/pageSeed`、`fallbackUsed`、`loading`、`error`
- `UserHistory`
  - `recentPlays`、`searchClicks`、`playSummaries`

前端服务边界建议固定为 5 个模块：

- `authService`：登录、会话恢复、登出
- `musicDiscoveryService`：搜索、推荐、热门、歌单内容
- `playbackService`：取可播资源、预校验、失败重试/跳过
- `historyService`：最近播放与行为摘要
- `playerStore`：播放器内核状态，不直接写请求逻辑

## Test Plan
必须覆盖这些验收场景：

- 登录成功后可进入主界面，重启应用后会话仍可恢复。
- 搜索歌曲后可立即播放，且搜索失败/空结果有明确反馈。
- 点击多首歌曲可形成连续播放队列，上一首/下一首行为正确。
- 进度拖动、音量调整、播放/暂停在真实音频资源下可工作。
- 单曲循环、列表循环、随机播放切换后，下一首逻辑符合预期。
- 首页推荐可展示内容，刷新后不会稳定返回完全相同的列表。
- 推荐为空或失败时可回退热门内容。
- 不可播歌曲不会中断整体体验，系统会提示并自动跳过。
- 最近播放在重新进入应用后仍可见，并能作为续播入口。
- 断网、超时、接口异常时，页面不白屏，播放器状态不丢失。

## Assumptions
- 真实接口能力由 `@neteasecloudmusicapienhanced/api` 提供，当前计划不新增独立后端。
- 渲染层直连接口是已确认策略，但请求仍需集中封装，避免页面组件直接散写。
- Electron 在首期只承担桌面容器角色；业务代码要尽量写在可迁移到网页端的渲染层。
- 首次实现不追求“推荐很聪明”，只追求“登录后能搜到、能播、能连续听、首页有内容可看”。
- 任务排期建议按 Phase 0 -> 1 -> 2 -> 3 -> 4 -> 5 顺序执行；其中 Phase 1 是第一个必须可演示的里程碑。
